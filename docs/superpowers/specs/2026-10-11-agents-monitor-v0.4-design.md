# agents-monitor v0.4（公開前の仕上げ）設計書

- 作成日: 2026-10-11
- 状態: 実装済み（feat/v0.4）
- 元の設計書: `2026-10-09-agents-monitor-design.md`、v0.2・v0.2.1・v0.3 の設計書
- 位置づけ: 配布（署名・公証・dmg・Homebrew・自動更新）の設計の前に、アプリの側を公開できる質にそろえる

## 1. 目的

公開したときの質を上げる。v0.3 までの機能は変えず、点検（2026-10-11）で見つかった不具合・無駄・文書の食い違いを直す。

### 成功の基準

- 状態の表示が実際とずれる既知の場面（中断の誤判定、サブエージェント、終了直後の状態不明など）がなくなる
- アプリを止めても、`~/.agents-monitor` が際限なく大きくならない
- 一覧を閉じている間の負荷とメモリーが、v0.3 より増えない（2-4・2-5 で減らす）
- README だけを読んだ人が、作り方・通知の許可・設定・消し方で迷わない
- 設計書の記述が実装と食い違わない

### 対象外

- 配布にかかわること（正式な署名と公証、Intel と Apple Silicon の両方で動くアプリ、Gatekeeper の案内、ダウンロードの案内）。配布の設計で扱う
- Codex と macOS 以外への対応。方向性だけを付録 A に書く
- 新しい機能

### 判断の前提

- 常駐するアプリなので、定期的な処理・外部コマンド・描き直しは負荷を見積もってから入れる。軽さのためにやむを得ず妥協するときは、ユーザーに確かめる
- アプリの操作で Claude Code のセッションを作らない
- Claude Code の設定ファイルは直接書き換えない

## 2. 点検の結果と作りの見直し（2026-10-11）

似たアプリ（cc-status-bar、Claude Watch、claude-status-bar、c9watch、so-agentbar など）と作りを比べた。根本から変えるべきところはなかった。

| 今の作り | 比べた結果 |
|---|---|
| hook → イベントのファイル → アプリ | 多くのアプリと同じ。会話の記録（jsonl）だけを読む方法は、記録の形が公開された仕様でないため壊れやすい |
| プラグインを `claude plugin` で入れる | 他のアプリはどれも `settings.json` を直接書き換えている。プラグインの方が、利用者の設定に触れず、きれいに外せる |
| Tauri | 他のアプリの多くは Swift。メモリーは合計 約 64MB（本体 24MB、WebKit 約 40MB）で、Swift なら 20〜30MB の見込み。作り直すほどの差ではなく、macOS 以外の道も残るので変えない。2-5 で減らす |
| 3 秒ごとのプロセスの確認 | 状態不明の行を見つけるために全体を読んでいる。2-4 で、一覧を閉じている間は知っている pid だけにする |
| イベントのフォルダーを 1 秒ごとに読む | ほぼ空のフォルダーを読むだけで負荷はわずか。macOS に知らせてもらう形（kqueue）は、複雑さに見合わないので入れない |
| `open -a` で前面に出す | タブまで選ぶアプリは AppleScript やアクセシビリティの許可を使う。v0.3 の方針（配布の後に検討）のまま |

## 3. 状態の正しさ

### 3.1 中断の誤判定

- 会話の記録の最後のメッセージ行が、利用者の入力の文（`type` が `user` で、内容が文字列、または `type` が `text` の要素）で、その文が `[Request interrupted by user` で**始まる**ときだけ中断とみなす
- ツールの結果（`tool_result`）の中に目印の文字があっても中断とみなさない
- 読む量は今と同じ（末尾 64KB）

### 3.2 アプリを止めたときにイベントのファイルが増え続ける

- hook は書く前にイベントのフォルダーのファイルを数え、`MAX_SPOOL_FILES` 以上なら書かない
- アプリが動いていればフォルダーはほぼ空なので、数える負荷はわずか
- README に消し方を書く（7 章）

### 3.3 会話以外の実行を除く

- hook は、親をたどって見つけた `claude` の引数に `-p` か `--print` があれば何も書かない（`is_interactive_session` を使う）
- `CLAUDE_CODE_ENTRYPOINT` が `sdk-` で始まるとき（Agent SDK から動かしたとき）も何も書かない。値は実装の最初に実物で確かめる（9 章）
- VS Code 拡張の `claude` には `-p` が付かないことを確認済み

### 3.4 pid が一度も分からなかったセッション

- hook が親をたどって `claude` を見つけられないと pid がない（`claude` を別の名前で動かしている、など）。一度でも見つかれば pid を使い続けるので、ふだんは起きない
- pid がなく、最後の知らせから 24 時間たったセッションは「終了」として扱う。その後はほかの終了と同じく一覧から消える
- pid があるセッションは、何もしていなくてもプロセスが動いている間は残る（今と同じ）

### 3.5 サブエージェント

- 数（`active_subagents`）をやめ、動いているサブエージェントの `agent_id` の集まりで持つ
- `SubagentStart` で加え、`SubagentStop` で除く。対応する開始のない終了は何もしない
- `SessionStart`（`compact` を除く）で空にする
- 保存の形が変わる。前の版の `state.json` は読めるようにし（新しい項目は `serde(default)`、古い数は捨てる）、空から始める

### 3.6 終了直後の状態不明の行

- 終了してから 30 秒以内のセッションの pid も「知っている pid」とし、状態不明の行を作らない（終了の後片付けの間や `/clear` の間）

### 3.7 時刻の比べ方のずれ

- 中断と判定したとき（`detect_interrupts`）は、状態が変わった時刻を `now_ms` ではなく「最後の知らせの時刻 + 1」にする
- これで、判定の直前に書かれて、直後に読まれた入力の知らせが捨てられない
- プロセスがなくなって終了としたとき（`mark_ended`）は `now_ms` のままにする。終了の後は `SessionStart` のほかは受け付けないのでずれは起きず、3.6 の 30 秒の猶予は終了した時刻から数える必要があるため

## 4. 軽さ

### 4.1 メニューバーのアイコン

- 前に描いた状態を覚え、変わったときだけ `set_icon_with_as_template` を呼ぶ

### 4.2 起動時に `claude` を動かす回数

- 計画が空（直すことがない）なら、確かめ直しを飛ばす。1 フォルダーにつき 6 回から 4 回に減る
- 存在しないフォルダーでは `claude` を動かさない

### 4.3 設定の保存

- 「ログイン時に起動」は、その値が変わったときだけ書き直す

### 4.4 3 秒ごとのプロセスの確認

- 一覧を閉じている間は、全プロセスを読まない。知っているセッションの pid だけについて、動いているかと、`claude` のままか（`KERN_PROCARGS2` の引数）を確かめる
- 全プロセスを読むのは、一覧を開いている間（開いた直後と、その後 3 秒ごと）だけにする。全体を読むのは状態不明の行を見つけるためで、状態不明はアイコンにも通知にも関わらない
- 直す前と後で CPU の使用量を測る。差がほとんどなければこの変更は取りやめ、そのことを報告する

### 4.5 WebKit のメモリー

- 一覧を閉じたら画面（webview）を捨て、開くときに作り直す形を試す
- 減ったメモリーと、開くまでの時間を測る。開くのが目に見えて遅くなるなら、採るかどうかをユーザーと決める
- 結果（2026-10-12）: 閉じたら捨てる形を採った。開いて閉じた後は 約 59MB → 約 42MB、開く速さは体感で変わらない
- 起動したときに一覧を作らない形も試したが、最初に開くときに WebKit のプロセスを 3 つとも起動するので、ログインして最初の 1 回が遅く感じた。減るのは最初に開くまでの間だけなので、起動したときに作る形に戻した（ユーザーと決定）

## 5. 堅牢さ

### 5.1 panic

- 監視の 1 回分の処理（`run_tick`）で panic が起きても、その回を捨てて次から続ける
- panic の内容は `~/.agents-monitor/crash.log` に書く。書くのは panic のときだけで、64KB を超えたら古い分を消す
- Mutex が壊れても（poison）中身を取り出して使い続ける

### 5.2 設定の連続操作

- 画面の側で最新の設定を持ち、保存は順番に 1 つずつ行う。古い設定で上書きしない

### 5.3 調べもの用の生データ（`AGENTS_MONITOR_DEBUG_RAW`）

- 開発用として残す。README の「開発」と「保存するデータ」に、全文が保存されることと消し方を書く

## 付録 A. Codex と macOS 以外への対応の方向性（今は作らない）

### A.1 Codex

- 2026-10 の調べでは、Codex の hook は Claude Code とほぼ同じ（`SessionStart`（`source` 付き）・`SessionEnd`・`UserPromptSubmit`・`PreToolUse`・`PermissionRequest`・`PostToolUse`・`Stop`・`PreCompact`/`PostCompact`・`SubagentStart`/`Stop`・`Interrupt`）。`Notification` はない。共通の項目（`session_id`・`cwd`・`transcript_path`・`hook_event_name`）も同じ
- 今の分け方（hook の入口 → 共通のイベント → core の状態の変わり方）のまま、入口を足せばよい。イベントにエージェントの種類を持たせ、セッションの ID が衝突しないようにする
- `Interrupt` があるので、Codex では会話の記録から中断を推測しなくてよい
- 導入の違い: Codex のプラグインも `hooks/hooks.json` を持つが、CLI で入れるコマンドがなく（対話の `/plugins` から入れる）、管理されていない hook は `/hooks` での確認が要る。自動では入れられないので、手順を案内する形になる
- 移動: Codex の VS Code 拡張（`openai.chatgpt`）でも、親をたどって `.app` を見つける今の方法が使える見込み
- 1.0.0 の前に対応する

### A.2 macOS 以外

- core はほぼ OS に依らない。プロセスの情報（`procinfo.rs`）は macOS 専用で、`ps.rs` に `ps`・`lsof` の経路を残してある
- OS ごとに要るのは、通知（`notifier.rs`）、移動（`jumper.rs`）、プラグインの場所と `claude` の探し方、ログイン時の起動
- Tauri は Windows と Linux でも動くので、画面はそのまま使える見込み。通知などで新しいライブラリが要るときは、そのときに確かめる
- 時期は未定。使う人が出てきたら検討する
