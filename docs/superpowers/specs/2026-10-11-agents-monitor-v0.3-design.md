## 1. 目的

一覧の行や通知を押したら、そのセッションが動いている画面を前面に出す。移動できない環境や、移動に失敗したときは、これまでどおり詳細を開くだけにし、「移動できません」などのメッセージは出さない。

### 成功の基準

- VS Code 系のエディター（VS Code・Windsurf・Cursor など）では、そのプロジェクトのウィンドウが前面に出る（会話のタブは選ばない。2.1 節）
- Terminal.app と iTerm2 では、そのアプリが前面に出る（タブは選ばない）
- 通知を押しても同じところへ移動する
- 移動できないときは、押すと詳細が開くだけで、エラーの表示は出ない

### 対象外

- tmux の中で動くセッションの移動（親をたどっても外側のターミナルにたどり着けず、tmux のクライアントからターミナルを探す処理が要るため。使う人がいれば後の段階で検討する）
- ターミナルのタブの選択（AppleScript とオートメーションの許可が要り、ad-hoc 署名の間は作り直すたびに許可が消えるおそれがあるため。正式な署名を入れる配布の後に検討する）
- Ghostty・WezTerm・Warp などの個別の対応（アプリを前面に出すところまでは、次の「そのほかのアプリ」で共通に扱う）

## 2. 調べてわかったこと（2026-10-11）

（1〜5 行目は設計の時点のもの。会話のタブまで選ぶ方法は、実装後の確認で取りやめた。2.1 節）

- Claude Code の VS Code 拡張（2.1.296）は URI ハンドラーを持つ。`<スキーム>://anthropic.claude-code/open?session=<セッション ID>` を開くと、その会話をエディターのタブで開く（中では `claude-vscode.primaryEditor.open` を呼ぶ）
- 先に `open -b <バンドル ID> <プロジェクトのフォルダー>` でそのフォルダーのウィンドウを前面に出してから URI を開くと、正しいウィンドウでその会話のタブが前に出た（VS Code で確認。すでに開いている会話のタブが選ばれ、タブは増えなかった）
- 初回だけ、VS Code が「'Claude Code for VS Code' 拡張機能がこの URI を開くことを許可しますか?」と確認する。「今後、この拡張機能についてメッセージを表示しない」にチェックを入れて開くと、次からは出ない。アプリの側からは消せないので README で案内する
- URI のスキームは、アプリの `Contents/Info.plist` の `CFBundleURLTypes` → `CFBundleURLSchemes` にある（VS Code は `vscode`）。`plutil -extract CFBundleURLTypes json -o - <Info.plist>` で読める
- VS Code 拡張の `claude` は拡張のフォルダー（`~/.vscode/extensions/…/native-binary/claude`）で動き、親は `Visual Studio Code.app` の中の拡張ホスト（`Code Helper (Plugin)`）。親をたどれば `.app` にたどり着く
- 会話を `--resume`／`--continue` で再開してもセッション ID は変わらない（v0.2 で確認）。開き直した会話にも同じ URI で移動できる

### 2.1 会話のタブまで選ぶのをやめた理由（2026-10-11、実装後の確認）

- VS Code は拡張あての URI を「最後に使っていたウィンドウ」に渡す。`open -a` でウィンドウを前に出した直後に URI を送ると、切り替えが終わる前に届き、直前のウィンドウで開かれた
- 拡張は、開けと言われた会話がそのウィンドウにないと、空の新しい会話を作る（新しいタブと新しい `claude` のプロセスが生まれ、`SessionStart` が届く）
- そのため、移動のたびに別のウィンドウで空の会話が作られ、それが「完了（新規）」として通知され、その通知を押すとまた作られる、という連鎖が起きた
- 待つ時間を延ばすと多くは正しく届くが、保証はない。`code <フォルダー> --open-url <URI>` でも、URI は直前のウィンドウに届いた。拡張の URI にはウィンドウやフォルダーを指定する項目がない
- 勝手にセッションを作らないことを優先し、会話の URI は送らず、ウィンドウを前に出すだけにした（ユーザーと決定）。拡張がウィンドウの指定に対応したら、会話のタブまで選ぶ形に戻すことを検討する
- VS Code だけでウィンドウを切り替えても、セッションは作られなかった（アプリの操作が原因だったことの確認）

### 2.2 セッションの開始の知らせ

- `SessionStart` の入力の `source` は `startup`・`resume`・`clear`・`compact` のどれか。圧縮の後にも `compact` で届く
- `compact` では状態を変えない（v0.2 までは作業の途中で「完了（新規）」に戻っていた）。`resume` では「新規」と表示しない
- セッションが現れただけ（前の状態がない変化）では通知しない

## 3. 全体構成

移動先を決める判断は core の純粋な関数、`open` の実行はアプリに置く。v0.1・v0.2 と同じ分け方。

| 置き場所 | 役割 |
|---|---|
| core `jump` | セッションの情報とプロセスの親子関係から、移動先（`JumpTarget`）を決める。`.app` の見つけ方もここ |
| core `ps` | 親をたどる関数（v0.1 の `find_claude_ancestor` と同じ考え方）を、`.app` を探す用途に使えるようにする |
| アプリ `jumper` | 移動先に応じて `open` を実行する（5 秒で打ち切る） |
| アプリ `notifier` | 通知にセッション ID を持たせ、押されたら `jumper` を呼ぶ |
| 画面 | 行を押すと移動、詳細は行の右端のボタン。失敗したら詳細を開く |

### 3.1 移動先の決め方

押した時点で、`claude_pid` からプロセスの親をたどる（保存した情報ではなく、そのときのプロセス一覧を見る）。

| 移動先 | 条件 | 移動のしかた |
|---|---|---|
| アプリ | `TMUX_PANE` がなく、親をたどって `.app` が見つかった | `open -a <.app のパス>`。エディター（`entrypoint` が `claude-vscode`）では `open -a <.app のパス> <フォルダー>`。フォルダーはセッションを始めたときの `cwd`（Claude が `cd` しても変わらない）。開けなければアプリだけを前に出す |
| なし | tmux の中（`TMUX_PANE` がある）、`.app` が見つからない、プロセスがもうない | 何もせず、詳細を開く |

- `.app` は、親をたどる途中で見つかった実行ファイルのパスのうち、いちばん外側の `*.app` とする（VS Code の拡張ホストは `Visual Studio Code.app/Contents/Frameworks/Code Helper (Plugin).app/…` の奥で動くため、内側の `Code Helper (Plugin).app` を取らない）

- `open` に渡すフォルダーやアプリのパスはコマンドの引数として渡し、シェルを通さない
- アプリを開くときはバンドル ID ではなく `.app` のパスを使う（`open -a <パス>`）
- `ps` の `args` はスペースを含むパス（`/Applications/Visual Studio Code.app/…`）を区切らずに持つので、空白で分けずに、先頭から最初の `.app/` までを `.app` のパスとする

### 3.2 行の操作

- Agents タブの行を押すと、一覧ウィンドウを閉じてから移動する
- Unknown タブの行（状態不明）は移動しない。押すと詳細が開閉する（Figma の AgentListItem の Type=Unknown）
- 移動先が「なし」、または移動に失敗した（`open` が失敗した・5 秒で終わらない）ときは、一覧ウィンドウを開き直して、その行の詳細を開く（移動の前に一覧は閉じている）。理由は表示しない
- 詳細は、補助の文字の行の ∨ で開け閉めする。行を押す操作とは別にする（v0.2 のドラッグとも区別する。4px 動かしたらドラッグ）
- 行の右側は上下 2 段にする。上（プロジェクト名の行）に経過時間、下（補助の文字の行）に詳細の開閉ボタン（∨／∧）。経過時間を出さない状態でも、ボタンの位置は変えない。詳細を開いても、ボタンは 2 行目の高さのまま動かさない
- 見た目は Figma の「v0.3 下書き」（`131:609`）

### 3.3 通知の操作

- 通知を出すときに、通知の識別子を `session:<セッション ID>` にする（`userInfo` の辞書を組み立てずに済み、同じセッションの通知は新しいもので置き換わるので、古い通知が通知センターに溜まらない）
- 通知を押されたら（`UNUserNotificationCenterDelegate` の `didReceiveNotificationResponse`）、そのセッションへ 3.1 のとおりに移動する
- 移動先が「なし」・失敗・セッションがもうないときは、一覧ウィンドウを開き、その行があれば詳細を開く

## 4. エラー処理

| 場面 | 対処 |
|---|---|
| 移動先が「なし」 | 詳細を開くだけ。メッセージは出さない |
| `open` が失敗した・5 秒で終わらない | 詳細を開くだけ。理由はログ（標準エラー）にだけ出す |
| 通知を押した時点でアプリが別の状態（一覧が開いているなど） | 一覧を閉じてから移動する。失敗したら一覧を開いて詳細を出す |

## 5. テスト

- **core のユニットテスト**
  - 移動先の決め方: 3.1 節の表の各行（VS Code、Windsurf、Terminal.app、iTerm2、tmux、状態不明の行、プロセスがない）を、`ps` の出力を模したプロセスの親子関係で確かめる
  - いちばん外側の `.app` を取ること（`Code Helper (Plugin).app` を取らない）
- **実機確認**（この Mac で確かめられるもの）
  - VS Code: 2 つのウィンドウを開いた状態で、それぞれのプロジェクトのウィンドウが前に出る
  - Windsurf: そのプロジェクトのウィンドウが前に出る（Claude Code の拡張が入っていれば）
  - Terminal.app・iTerm2: アプリが前面に出る
  - tmux: 押すと詳細が開くだけ
  - 通知を押して移動できる
  - 移動に失敗する場面（アプリを終了してから押す）で詳細が開く
- Cursor はこの Mac に入っていないので確かめない（親をたどって `.app` を見つける同じ仕組みで動く見込み）

## 6. 実装の最初に確かめること

- 通知を押したときに、アプリ（Accessory のメニューバーアプリ）が `didReceiveNotificationResponse` を受け取れるか。アプリが起動していないときに押した場合の動き
- VS Code で同じフォルダーを 2 つのウィンドウで開いている場合に、どちらへ行くか（そのまま受け入れる）

結果に応じて 3.1・3.3 節を調整する。
